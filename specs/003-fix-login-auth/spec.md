# Feature Specification: 登录授权验证修复

**Feature Branch**: `003-fix-login-auth`

**Created**: 2026-06-01

**Status**: Draft

**Input**: User description: "当前关于login有几种方式，一个是默认直接login，一个qrcode，一个是--web,一个是指定浏览器，但是都有问题，完全授权验证不了"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 所有登录方式必须完成授权验证 (Priority: P1)

作为 CLI 用户，我希望无论选择默认登录、二维码登录、网页登录还是指定浏览器登录，工具都必须确认当前凭证真的能访问受保护资源后才提示登录成功，这样我不会得到一个看似成功但后续命令不可用的登录状态。

**Why this priority**: 当前核心问题是多种登录入口都无法完成完整授权验证。统一的成功标准是修复登录体验的基础，否则任何单一路径即使保存了凭证也不能证明用户已可用。

**Independent Test**: 分别执行每一种登录入口，登录成功后立即执行一个需要身份授权的用户信息检查；只有该检查通过并返回当前账号信息时，登录才算成功。

**Acceptance Scenarios**:

1. **Given** 用户通过任一登录方式提交登录，**When** 工具获得候选凭证，**Then** 工具必须验证该凭证可访问受保护的当前用户信息后，才显示登录成功。
2. **Given** 候选凭证缺少关键授权信息或无法访问受保护资源，**When** 登录流程结束，**Then** 工具不得保存该凭证为有效登录状态，并必须提示授权验证失败及下一步操作。
3. **Given** 授权验证服务暂时不可用，**When** 用户尝试登录，**Then** 工具必须明确说明验证未完成，不得把未知状态当作登录成功。

---

### User Story 2 - 默认 login 自动完成可用登录 (Priority: P1)

作为 CLI 用户，我希望直接运行 `boss login` 时，工具能使用默认登录路径完成完整授权验证，并在失败时清楚说明为什么失败和可以改用哪种方式。

**Why this priority**: 默认 login 是用户最自然、最常用的入口。它必须代表最可靠的登录体验，而不是进入一个无法验证的中间状态。

**Independent Test**: 在已有有效浏览器会话、无有效浏览器会话、凭证过期三种环境中分别运行 `boss login`，确认结果与提示都符合预期。

**Acceptance Scenarios**:

1. **Given** 用户本机存在可用的已登录会话，**When** 运行 `boss login`，**Then** 工具完成授权验证并展示当前账号身份。
2. **Given** 用户本机不存在可用会话，**When** 运行 `boss login`，**Then** 工具明确提示未找到可验证的登录状态，并列出二维码和网页登录作为可选下一步。
3. **Given** 默认登录获得的凭证已过期，**When** 工具验证授权，**Then** 工具提示凭证过期或授权失效，并不得覆盖已有有效凭证，除非新凭证已验证通过。

---

### User Story 3 - 二维码登录必须从扫码到授权闭环 (Priority: P2)

作为 CLI 用户，我希望 `boss login --qrcode` 不只显示二维码，还能正确识别扫码、确认、授权完成和超时等状态，最终保存经过验证的登录凭证。

**Why this priority**: 二维码登录是浏览器会话不可用时的重要替代路径，尤其适用于远程终端和无图形界面环境。

**Independent Test**: 运行 `boss login --qrcode`，分别测试正常扫码确认、扫码后未确认、二维码超时、用户取消四种情况。

**Acceptance Scenarios**:

1. **Given** 用户运行 `boss login --qrcode`，**When** 二维码生成，**Then** 用户可以在终端看到可扫码内容和过期时间。
2. **Given** 用户已扫码但未在 App 中确认，**When** 工具等待授权，**Then** 工具显示等待确认状态，不得提前宣称登录成功。
3. **Given** 用户扫码并确认登录，**When** 工具收到授权结果，**Then** 工具验证凭证可访问当前用户信息并保存登录状态。
4. **Given** 二维码过期或用户取消，**When** 登录流程结束，**Then** 工具清理临时状态并提示登录未完成。

---

### User Story 4 - Web 登录必须完成浏览器到 CLI 的授权回收 (Priority: P2)

作为 CLI 用户，我希望 `boss login --web` 能打开登录页面，并在我完成网页登录后让 CLI 自动获得并验证授权结果，而不是停留在浏览器已登录但 CLI 未登录的状态。

**Why this priority**: Web 登录是没有 App 或不适合提取浏览器 Cookie 时的重要路径，必须能把网页授权结果可靠带回 CLI。

**Independent Test**: 运行 `boss login --web`，测试成功登录、用户关闭浏览器、回收超时、回收结果无效四种情况。

**Acceptance Scenarios**:

1. **Given** 用户运行 `boss login --web`，**When** 命令启动，**Then** 工具打开或提供登录页面，并提示用户在浏览器完成登录。
2. **Given** 用户在浏览器完成登录，**When** 授权结果返回 CLI，**Then** 工具验证凭证并显示当前账号身份。
3. **Given** 用户关闭页面或超时未完成登录，**When** 登录流程结束，**Then** 工具提示网页登录未完成，并说明可重试或改用二维码登录。
4. **Given** 浏览器已显示登录成功但 CLI 未获得可验证凭证，**When** 工具检测结果，**Then** 工具必须将其视为登录失败并给出诊断提示。

---

### User Story 5 - 指定浏览器登录必须尊重用户选择 (Priority: P3)

作为 CLI 用户，我希望通过参数指定浏览器时，工具只从我指定的浏览器获取登录状态，并清楚说明该浏览器是否存在可验证授权。

**Why this priority**: 多浏览器、多账号和多配置文件环境下，用户需要可控地选择登录来源，避免使用错误账号或错误会话。

**Independent Test**: 在多个浏览器或多个账号同时存在的环境中执行指定浏览器登录，确认工具验证的是用户指定来源。

**Acceptance Scenarios**:

1. **Given** 用户指定某个浏览器且该浏览器已登录，**When** 运行登录命令，**Then** 工具从该浏览器获取候选凭证并完成授权验证。
2. **Given** 用户指定的浏览器未安装、未登录或会话不可用，**When** 运行登录命令，**Then** 工具只报告该指定来源不可用，不得静默改用其他浏览器。
3. **Given** 指定浏览器中存在多个可选会话，**When** 工具无法确定唯一账号，**Then** 工具必须提示用户选择或提供更明确的来源。

### Edge Cases

- 候选凭证格式完整但服务端拒绝授权，应显示授权验证失败并保留原有有效凭证。
- 用户中途取消任一登录方式，应清理临时状态并返回非成功结果。
- 登录成功后的账号身份与用户预期不一致时，用户应能立即退出并重新选择方式登录。
- 网络连接中断或服务端响应异常时，应区分"无法验证"与"验证失败"，避免误导用户。
- 本地已有凭证有效而新登录尝试失败时，不应破坏原有可用登录状态。
- 多个登录命令同时运行时，不应互相覆盖未验证或部分完成的凭证。
- 指定浏览器、默认登录、二维码和 Web 登录的错误提示应能说明失败阶段：获取凭证、等待授权、验证授权或保存凭证。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为默认登录、二维码登录、Web 登录和指定浏览器登录定义同一个登录成功标准：凭证通过授权验证并能识别当前账号。
- **FR-002**: 系统 MUST 在保存新登录凭证前完成授权验证；未验证、验证失败或验证状态未知的凭证不得成为有效登录状态。
- **FR-003**: 系统 MUST 支持直接运行 `boss login` 的默认登录方式，并在成功时展示当前账号身份。
- **FR-004**: 系统 MUST 支持 `boss login --qrcode` 的二维码登录方式，并覆盖二维码生成、扫码、确认、授权完成、超时和取消状态。
- **FR-005**: 系统 MUST 支持 `boss login --web` 的网页登录方式，并能判断网页登录结果是否成功回收到 CLI。
- **FR-006**: 系统 MUST 支持用户指定浏览器作为登录来源，并在指定来源不可用时给出明确失败信息，不得未经用户确认改用其他来源。
- **FR-007**: 系统 MUST 在登录失败时按失败阶段提供可操作的中文提示，包括获取凭证失败、等待用户授权、授权验证失败、保存凭证失败。
- **FR-008**: 系统 MUST 在新登录尝试失败时保留既有的有效登录状态，除非用户明确退出登录或新凭证已验证成功。
- **FR-009**: 系统 MUST 在登录成功后提供可独立验证的状态检查，让用户确认当前账号身份和登录来源。
- **FR-010**: 系统 MUST 支持用户取消或超时退出任一登录流程，并确保不会留下部分完成的登录状态。
- **FR-011**: 系统 MUST 在检测到本地凭证失效时引导用户重新登录，并说明可用的登录方式。
- **FR-012**: 系统 MUST 对所有登录方式记录足够的诊断信息供用户定位问题，但不得暴露敏感凭证内容。

### Key Entities

- **登录尝试 (Login Attempt)**：一次用户发起的登录流程，包含选择的登录方式、当前阶段、开始时间、结束结果和失败原因。
- **候选凭证 (Candidate Credential)**：登录方式产生但尚未验证的凭证，只能用于授权验证，不能直接作为有效登录状态。
- **有效登录状态 (Authenticated Session)**：已通过授权验证并保存的本地登录状态，包含登录来源、账号身份摘要、创建时间和有效性状态。
- **授权验证结果 (Authorization Verification Result)**：对候选凭证进行验证后的结果，包含成功、失败、未知、失败阶段和用户可见提示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的登录成功提示都对应一个已通过授权验证的当前账号身份。
- **SC-002**: 默认登录、二维码登录、Web 登录和指定浏览器登录四种入口均可独立完成成功、失败、取消和超时场景测试。
- **SC-003**: 授权失败时，用户能在错误提示中看到失败阶段和至少一个可执行下一步，且无需查看源码或调试日志。
- **SC-004**: 新登录尝试失败时，已有有效登录状态在 100% 的测试场景中保持可用。
- **SC-005**: 用户完成任一成功登录后，立即运行需要授权的命令应在 5 秒内确认当前账号可用。
- **SC-006**: 二维码和 Web 登录在用户未完成授权的情况下，均不会产生任何持久化的有效登录状态。

## Assumptions

- 用户已有合法的 BOSS直聘账号，并通过网页端或 App 端完成授权。
- "完整授权验证"指 CLI 能使用登录结果访问受保护的当前用户身份信息，而不只是获得 Cookie、二维码状态或网页跳转结果。
- 默认 `boss login` 优先使用现有本机会话完成登录；如果无法得到可验证授权，则提示用户选择二维码或 Web 登录。
- 指定浏览器登录是用户显式选择的来源，失败时不自动切换到其他浏览器。
- 本功能聚焦登录授权闭环和用户可见结果，不扩大到账号注册、密码找回或多账号管理。

## Dependencies

- **外部依赖**: BOSS直聘 登录、扫码确认和当前用户身份验证服务可用。
- **外部依赖**: 用户所在环境允许所选登录方式完成必要的人机交互，例如扫码、浏览器页面或本机浏览器会话。
- **内部依赖**: 本地凭证保存、读取和清理能力能够区分候选凭证与已验证凭证。
